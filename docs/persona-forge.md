# Persona Forge · 开发笔记

> 记录 Persona Forge skill 的改版历程、架构决策、已知问题与未来方向。
> 不是使用手册，是开发者的内部备忘录。

---

## 一、项目定位

**Persona Forge** 是一个人格化引擎，具备两种核心能力：

1. **人物蒸馏**：将真实人物的思维方式提炼为可运行的 `*-perspective` Skill
2. **角色合成**：从维度库组合出全新人格化角色 `*-persona`

区别于单纯的「角色扮演 prompt」，Persona Forge 输出的是**自包含的、可独立运行的 Skill 文件**（SKILL.md + references + 软链接），可被 Claude Code 自动识别和激活。

**前身**：`nuwa-skill`（女娲造人），2026-05 全面品牌重塑为 Persona Forge。

## 二、版本历史

### v2.1（2026-05-21）—— 角色合成确认流程修复

**问题**：Path C（角色合成）Phase 0C 的步骤 2-4 在实际执行时容易被跳过——系统基于"描述足够明确"的判断，直接推导维度组合、假设场景、自动命名并创建目录，用户失去参与机会。

**修复**：
- Step 2 新增**硬规则**：无论用户描述多明确，不可跳过维度组合展示与确认
- 流程改为"自动推导推荐组合 → 展示给用户 → 确认/调整后推进"
- Step 1/3 增加判定分支：信息已含则复述确认，未含则必须追问
- Step 4 强调必须获得用户确认后才能创建目录
- "绝不做的事"新增：禁止跳过 Phase 0C 用户确认

**涉及文件**：`SKILL.md`、`references/path-c.md`

---

## 三、当前架构

### 三路径入口分流

```
用户输入
├── 明确人名/主题 ────────→ Path A: 人物蒸馏
├── 角色描述/合成需求 ────→ Path C: 角色合成
└── 模糊需求 ─────────────→ Path B: 需求诊断 → 指向 A 或 C
```

### 路径对比

| 组件 | Path A（人物蒸馏） | Path C（角色合成） |
|------|-------------------|-------------------|
| Phase 0 | 0A: 直接路径 | 0C: 角色定义 |
| Phase 1 | 6 Agent 并行调研 | 1C: 1 Agent 领域知识注入 |
| Phase 2 | 从真实言行提炼心智模型 | 从维度组合推导心智模型 |
| Phase 3 | 填充人物 Skill 模板 | 填充合成角色 Skill 模板 |
| Phase 4 | 3 类质量验证 | 3 类角色一致性测试 |
| Phase 5 | 双 Agent 精炼 | 双 Agent 精炼（维度视角） |
| 输出模板 | 人物 Skill 模板 | 合成角色 Skill 模板 |
| 耗时 | 长（多 Agent 调研） | 短（直接组装） |

### 参考文件索引

| 文件 | 内容 | 维护责任 |
|------|------|---------|
| `references/path-a.md` | 人物蒸馏完整流程：Phase 1-5、Agent 模板、质量验证 | 人物蒸馏相关变更时更新 |
| `references/path-c.md` | 角色合成完整流程：Phase 0C-5C、维度推导、领域注入 | **角色合成相关变更时更新** |
| `references/skill-template.md` | 人物 Skill 模板 + 合成角色 Skill 模板 | 模板结构变更时更新 |
| `references/extraction-framework.md` | 心智模型三重验证方法论 | 提炼方法论变更时更新 |
| `references/persona-dimension-library.md` | 8 个预定义维度、冲突检测、协同推荐 | **新增维度或调整冲突规则时更新** |

## 五、未来扩展方向

### 5.1 近期（已识别需求）

- **维度库扩展**：增加 `patience_level`（耐心程度）、`strictness`（严格程度）、`formality`（正式程度）等维度
- **冲突检测自动化**：目前冲突检测靠规则表，可考虑在 SKILL.md 中用更结构化的方式描述，让运行时自动检测
- **角色合成测试覆盖**：增加更多典型场景的测试用例模板

### 5.2 中期（方向探索）

- **混合路径**："用费曼的风格教我数学"——将 Path A 提取的表达 DNA 作为 Path C 的维度输入
- **角色演进机制**：允许用户在使用中对角色提反馈，累积后触发角色自动更新
- **多语言角色**：当前维度库和模板中文优先，探索英文场景下的维度适配

### 5.3 远期（可能性）

- **角色市场**：用户创建的角色 skill 可导出、分享、评分
- **A/B 测试框架**：同一需求生成两个版本的角色，让用户对比选择
- **视频/播客角色**：不仅输出 text skill，还输出带 TTS 声音定义的多模态角色

## 六、关键决策记录

### 决策 1：为什么把源码和加载路径分开（`skills/` vs `.claude/skills/`）？

**时间**：项目初期
**决策**：skill 源码放在 `skills/<name>/`，通过软链接暴露到 `.claude/skills/<name>/`
**理由**：
- Claude Code 只从 `.claude/skills/` 加载，但把源码放这里会让仓库在 GitHub 上难以浏览
- 双路径让仓库既满足运行时加载需求，又保持 GitHub 可读性
- 便于跨项目复制 skill（不用区分 install vs source）

### 决策 2：为什么从 nuwa 改名为 Persona Forge？

**时间**：2026-05-20
**决策**：全面品牌重塑，脱离"女娲"中文品牌
**理由**：
- "女娲造人"暗示"创造生命"，有伦理敏感风险
- Persona Forge 更准确地描述"人格化引擎"的定位
- 英文名更利于国际化和代码命名（`persona-forge` 比 `nuwa-skill` 语义明确）

### 决策 3：为什么 Path C（角色合成）不搜索特定人物？

**时间**：2026-05-20
**决策**：合成角色只搜索领域通用知识，不搜索特定人物
**理由**：
- 合成角色是"创造"不是"模仿"，不需要特定人物的言行记录
- 避免用户误以为合成角色是基于某个真实人物
- 轻量化：1 Agent 5 分钟 vs 6 Agent 长时间调研

### 决策 4：为什么必须保留用户确认步骤？

**时间**：2026-05-21
**决策**：即使描述明确，Path C 也必须展示推荐组合并获确认
**理由**：
- 防止系统过度自信，替用户做选择
- 给用户参与感，提升最终角色满意度
- "描述明确"是系统判断，用户可能有隐性需求未表达

## 七、示例目录（examples/）

`examples/` 下收录了多个通过 Persona Forge 生成的 perspective skill 实例，用于：
- 展示输出质量基准
- 作为新开发者的参考模板
- 验证 skill 生成流程的端到端可行性

当前收录：Andrej Karpathy、Elon Musk、Feynman、Ilya Sutskever、MrBeast、Munger、Naval、Paul Graham、Steve Jobs、孙宇晨、X-Mastery Mentor、张一鸣、张雪峰 等。

**维护原则**：
- 每个 example 应包含完整的 `SKILL.md` + `references/research/`
- 旧 example 无需随主 skill 更新而更新（它们是历史快照）
- 新增 example 需跑通完整 Path A 流程
