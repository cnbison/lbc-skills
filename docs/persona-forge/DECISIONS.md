# 关键决策记录

## ADR-001: 从 nuwa 改名为 Persona Forge

- **日期**：2026-05-20
- **背景**：原品牌"女娲造人"暗示"创造生命"，有伦理敏感风险
- **决策**：全面品牌重塑为 Persona Forge
- **理由**：
  - "Persona Forge"更准确描述"人格化引擎"的技术定位
  - 英文名利于国际化和代码命名（`persona-forge` 语义明确）
  - 避免文化符号带来的误解
- **后果**：所有文档、目录、git 历史中的引用需同步更新
- **状态**：已执行

## ADR-002: 源码与加载路径分离（`skills/` vs `.claude/skills/`）

- **日期**：项目初期
- **背景**：Claude Code 只从 `.claude/skills/` 加载 skill
- **决策**：skill 源码放在 `skills/<name>/`，通过软链接暴露到 `.claude/skills/<name>/`
- **理由**：
  - 满足运行时加载需求
  - 保持 GitHub 仓库的可浏览性
  - 便于跨项目复制 skill（不用区分 install vs source）
- **后果**：每次新建 skill 必须同时创建目录和软链接，并都加入 git
- **状态**：已执行

## ADR-003: Path C（角色合成）不搜索特定人物

- **日期**：2026-05-20
- **背景**：设计角色合成路径时，需决定信息来源策略
- **决策**：合成角色只搜索领域通用知识，不搜索特定人物
- **理由**：
  - 合成角色是"创造"不是"模仿"，不需要特定人物的言行记录
  - 避免用户误以为合成角色是基于某个真实人物
  - 轻量化：1 Agent 5 分钟 vs 6 Agent 长时间调研
- **后果**：合成角色的"表达 DNA"需要组合设计，不能靠模仿
- **状态**：已执行

## ADR-004: 角色合成必须保留用户确认步骤

- **日期**：2026-05-21
- **背景**：实际执行中发现 Path C Phase 0C 步骤 2-4 被跳过，系统直接推导并创建角色
- **决策**：即使描述看似明确，也必须展示推荐维度组合并获得用户确认后才能推进
- **理由**：
  - 防止系统过度自信，替用户做选择
  - 给用户参与感，提升最终角色满意度
  - "描述明确"是系统判断，用户可能有隐性需求未表达
- **后果**： SKILL.md 和 path-c.md 中增加"硬规则"表述
- **状态**：已执行

## ADR-005: docs/ 目录规范化——按 skill 分目录的精简体系

- **日期**：2026-05-21
- **背景**：docs/ 平铺杂乱，各 skill 文档混合；需要记录开发过程信息
- **决策**：
  - 按 skill 分目录：`docs/<skill-name>/`
  - 每个 skill 只保留 2-3 个文件：README.md + CHANGELOG.md + DECISIONS.md（按需）
  - 取消 sessions/ 和 BACKLOG.md（避免重复记录）
  - 通用文档放入 `docs/_shared/`
  - 详细规则放在独立文档，CLAUDE.md 只保留一句话引用
- **理由**：
  - 记录价值 > 记录完整性
  - CHANGELOG.md 已足够承载过程摘要（git commit 保存代码 diff）
  - 避免 CLAUDE.md 膨胀，保持上下文友好
- **后果**：现有平铺文档需逐步迁移到新结构
- **状态**：已执行
